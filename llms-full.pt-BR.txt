# browser-automation-cli

> CLI one-shot de automação Chrome CDP para agentes de IA, sem daemon e sem telemetria remota.

browser-automation-cli é uma CLI Rust de processo único que lança Chrome ou Chromium do sistema via CDP, executa ações de browser do agente e depois finaliza e sai. Trabalho multi-passo deve usar `run --script` dentro de um processo para que refs `@eN` permaneçam válidas. Ciclo de vida: BORN, EXECUTE, FINALIZE, DIE.

Settings de produto são comandos, flags e XDG via `config path|init|show|set|get|list-keys` apenas. Logging usa `--verbose`/`--debug`/`-q` ou `config set log_level`. Cor usa `config set color true|false`. Chrome e Lighthouse usam path do shell ou `config set chrome_path|lighthouse_path`.

- Multi-passo via stdin: `run --script -` lê passos NDJSON do stdin, um por linha, contra uma única sessão viva
- Modo stdin continua one-shot: um BORN, um DIE, sem daemon; o chamador mantém a sessão viva enquanto o stdin ficar aberto

- Prefira stdin a process substitution do shell: `run --script <(printf ...)` é recusado porque o caminho cai em `/proc/<pid>/fd/<n>` fora das raízes permitidas

## Contrato de Settings
- Settings de produto: comandos, flags, XDG via `config path|init|show|set|get|list-keys` apenas
- Chaves importantes: dialog_settle_ms, chrome_path, lighthouse_path, openrouter_api_key, llm_base_url, llm_model, cache_backend, cache_redis_url, lang, log_level — referência completa com todas as **176** chaves em `docs/CONFIGURATION.pt-BR.md`; legível por máquina via `config list-keys --json`
- Encryption: `config set encryption_key` apenas
- Logging: `--verbose`/`--debug`/`-q` ou `config set log_level` / `log_to_file`
- Cor: `config set color true|false`
- Chrome / Lighthouse: path do shell ou `config set chrome_path` / `config set lighthouse_path` (mais flag lighthouse)
- Settle de diálogo: `config set dialog_settle_ms`; dialog accept|dismiss reporta `.data.dialog_settled`; isolamento multi-aba por session_id
- Cache Redis: `config set cache_backend redis` + `cache_redis_url` (somente `redis://`; `rediss://` fail-closed); doctor `cache_redis`

## Bases de Contrato
- Envelope de sucesso: `{"schema_version":1,"ok":true,"data":...}`
- Envelope de erro com `--json`: `{"schema_version":1,"ok":false,"error":{...}}` (fail-fast multi-passo pode incluir `data.steps` parciais)
- Erros de usage do clap com `--json` no argv também emitem envelopes JSON de erro (GAP-002)
- Sucesso de `run --json` inclui `ok` e o `steps[].data` completo (GAP-020)
- Stream `--json-steps` (durante `run`): uma linha NDJSON por passo com `step`, `cmd`, `ok`, `result`
- Exit codes incluem 0, 2, 65, 66, 69, 70, 74, 78, 124, 130, 141, 255; o enum vivo de `error.kind` é usage, data, no-input, unavailable, software, browser, protocol, timeout, cancelled, broken-pipe, config, io, então 255 é caminho fatal NÃO mapeado por nenhum `error.kind`
- Fragmentos de schema ao vivo: `browser-automation-cli schema <name> --json` ou `schema --cmd <name> --json`
